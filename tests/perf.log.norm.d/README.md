# perf.log.norm.d — normalized per-commit perf series

One `*-timing.json` per commit for the 82 commits in `v0.6.10..226836b`, all
measured by **one pinned harness against one pinned instruction bank**, so the
only thing that varies between runs is the engine itself.

Generated by `scripts/sweep/sweep.sh` (see `commits.order` for the commit order).
Re-run that script to add newly-landed commits: it only does the missing work.

## Method

* **Pinned to the newest revision, identical for all 82 runs:** `benchmark/`
  (the 1569-instruction bank + its loader) and `tests/test_perf_ratchet.py`
  (the harness, including its `reps=600 x 3 batches` timing loop).
  Everything under `microtaint/` is the commit under test.
* `uv.lock` and `pyproject.toml` are byte-identical across the whole range, so
  dependencies and compile flags (`-O3 -march=native -flto`) are constant too.
* **Two phases.** All 82 commits are built first (4 parallel workers, each
  snapshotted), then measured from those snapshots. No compiling ever runs
  during a measurement.
* **Two measurement workers**, pinned to cpu 2 and cpu 10 — distinct physical
  cores in *separate L3 domains* (cpus 0-7 and 8-15 on this Ryzen 7 5700U).
  A third worker would have had to share an L3, making contention depend on
  which worker picked up a commit.
* CPU: `scaling_governor=performance`, boost disabled -> all cores held at
  1776 MHz, so there is no frequency sag under load. The plot titles the run
  with the CPU model and clock rather than the machine name.

## Two adaptations (applied once, identically to every commit)

1. The harness skips an instruction whose rule an engine revision cannot build,
   recording it in the log's `skipped` list, instead of aborting the run.
2. The bank loader drops an ISA group whose register geometry the engine cannot
   construct. The SIMD profiles need `microtaint.debug.reg_aliases`, which only
   appears at commit 18/82, so the first 17 commits carry the 1535 scalar
   instructions and no SIMD. The scalar corpus is identical across all 82.

`skipped` was empty for every run: no instruction failed on any revision.

## Validated

Three commits (oldest / middle / newest) were re-measured **solo** and compared
against their 2-worker values: deltas within +-3.4%, mostly under 1.5%, with no
consistent sign. The parallelism adds noise well below the 80-98% effects.

## What this does and does not measure

The harness times `circuit.evaluate` -- taint propagation for one instruction --
and nothing else. It never runs the emulator, so a commit that optimises the
**hook / emulation path** shows up here as flat, no matter how much it helps
end to end. `1ed45c7` (v0.6.14, "read input registers via a C fnptr -> e2e -9%")
touches only `emulator/hook_core.pyx` and `emulator/wrapper.py`: its gain is
real, and invisible in this plot by construction. Check what a commit actually
touches before reading its step:

    git diff --stat <prev> <commit> -- microtaint/

## Noise floor: how to read small steps

`df218fc`, `e2041ba` and `746aac1` are a control triple -- the latter two change
only tooling and docs, so `git diff df218fc 746aac1 -- microtaint/` is empty and
all three runs measure the *same binary*. Their spread is pure measurement noise:

| quantity | across the three identical-engine runs |
|---|---|
| `cells` / `assigns` / `nodes` totals | **identical** (2110 / 3480 / 162265) |
| ns p50 | 2310 / 2201 / 2124 -> **8.8% spread** |
| ns p100 (pairwise) | up to +42% |
| per-instruction \|delta\| | median 3.3%, p90 34.6%, max 74.5% |

So the deterministic metrics are exactly reproducible, which is why the plot's
vertical rules are trustworthy even where the ns curves wobble. Wall clock is
not: **p50 carries roughly +-9%, and p100 is a single instruction's timing that
swings +-40%.** Read the big structural steps -- the ones that persist across
several commits or come with a vertical rule -- and treat an isolated sub-10%
p50 step or a sub-40% p100 step as noise.
